# FinSpace 0.2 final hardening evidence report

This report records the measured evidence for research-hardening steps 16 through 30. It complements `EVIDENCE_REPORT.md`, which records the original correctness, scaling, baseline, recovery, replay, and finance-integration campaign.

The machine-readable source of truth is generated by:

```bash
python -m experiments.final_reproduce --output evidence/generated
```

The final command first reruns the original evidence suite, then runs `experiments/final_hardening.py`, verifies SHA-256 checksums for the generated files, and builds a deterministic evidence ZIP.

## Weighted exact sampling

The reference campaign used a three-object space with exact integer weights `1, 3, 6`.

The exact replacement probabilities were therefore:

| Rank | Exact probability | Empirical probability, 20,000 draws | Absolute error |
|---:|---:|---:|---:|
| 0 | 1/10 | 0.0980 | 0.0020 |
| 1 | 3/10 | 0.3015 | 0.0015 |
| 2 | 3/5 | 0.6005 | 0.0005 |

The empirical frequencies are descriptive rather than the correctness oracle. The exactness claim is based on integer-ticket selection and exact rational probabilities. The same fixed seed reproduces the same sequence. A without-replacement draw over the three positive-weight ranks returned three distinct ranks.

Object-level weighted sampling deliberately materializes one integer weight per object and exposes an explicit domain-size cap when weights are derived from a function.

## Allocation strategies

The allocation experiment used 120 ranks, six workers, and a deliberately heterogeneous synthetic cost profile. Every tested strategy produced complete coverage with zero duplicate ranks and exactly 20 ranks per worker.

| Strategy | Worker costs | Maximum cost imbalance |
|---|---|---:|
| contiguous | 200, 200, 200, 60, 60, 20 | 180 |
| permuted | 200, 200, 74, 48, 60, 158 | 152 |
| strided | 124, 124, 124, 124, 122, 122 | 2 |

This experiment establishes exact allocation and demonstrates that allocation policy can materially change a structured synthetic workload. It does **not** establish a universal performance ranking. Real scenario runtimes can have very different structure, and the permutation is a reproducible affine bijection rather than a load-balancing oracle.

## Schema evolution

Two controlled schema edits were tested against a three-object base space.

### Append-only value extension

Adding a fourth value preserved all three existing canonical records at their previous ranks:

- preserved records: 3
- stable ranks: 3
- rank churn: 0
- added new ranks: 1
- removed old ranks: 0

### Value reordering

Reordering the same three values preserved all three canonical records but moved every one of their dense ranks:

- preserved records: 3
- stable ranks: 0
- rank churn: 3
- rank-churn fraction: 1.0

This is the intended result. FinSpace does not promise arbitrary rank stability. It produces an explicit compatibility map for surviving canonical objects.

## Exact finite table constraints

A 3-by-3 currency/engine Cartesian domain had nine syntactic candidates. A four-row `TableConstraint` admitted exactly four records:

- USD / analytic
- USD / finite difference
- EUR / analytic
- JPY / tree

The compiled domain contained exactly four valid objects and five compiled states. Invalid complete tuples were rejected by `Space.rank()`, and incompatible partial branches were pruned during compilation.

This is finite relation support, not a claim that FinSpace is a general SMT solver.

## Retry recovery

A 20-object campaign used a callable deliberately constructed to fail on the first attempt for every object and succeed on the second. With `max_retries=1`:

- submitted ranks: 20
- completed ranks: 20
- failed ranks: 0
- recorded retries: 20
- recorded attempts per completed rank: 2

A separate test establishes that a rank left in failed state remains eligible for later execution and is not mistaken for a completed rank during resume.

## Rank integrity

The protected-handle experiment established all four expected outcomes:

- an untampered checksum handle verified;
- changing the encoded rank caused checksum verification to fail;
- an HMAC handle verified with the original key;
- the same HMAC handle failed with a different key.

Checksum mode is designed to detect accidental corruption. HMAC mode adds keyed authenticity. Raw dense ranks provide neither property, and protected handles do not provide confidentiality.

## Canonical-rank shrinking

The shrinking experiment started from failing rank 91 with a predicate that fails for values greater than or equal to 23. The shrinker found rank 23 after 25 predicate evaluations and reported a complete prefix search.

The result proves deterministic shrinking under canonical rank order for that predicate. It does not claim that rank 23 is the universally simplest semantic representation of the failure.

## Generic invalid-record mutations

Starting from a valid FIX market order, the generic mutation generator produced 15 malformed variants covering:

- unknown fields;
- missing required active fields;
- invalid field values;
- activation of fields that should be inactive for the selected order type.

All 15 were rejected by the real FinSpace rank/validation path. Zero generated mutations were accepted.

## Campaign manifests

A campaign manifest bound a deterministic selection strategy, seed, worker count, adapter identity, oracle configuration, environment manifest, and external-data snapshot identifier to the exact space.

The manifest validated against the source space and produced distinct semantic and full-manifest digests. The semantic digest intentionally excludes the creation timestamp so semantically identical campaign definitions can be compared independently of file creation time.

## Artifact integrity and deterministic packaging

The complete reproduction command writes:

- original JSON and CSV evidence;
- `final_hardening.json`;
- `SUMMARY.md`;
- `MANIFEST.json`;
- `SHA256SUMS.txt`;
- `finspace-evidence.zip`.

The command verifies every data file against its SHA-256 manifest before constructing the final archive. The ZIP writer normalizes path order, timestamps, permissions, compression settings, and file bytes for deterministic packaging.

## Interpretation

The 0.2 hardening campaign strengthens the claim that FinSpace is an auditable execution and evidence layer over exact bounded financial domains. It intentionally avoids several stronger claims:

- weighted selection is not automatically a market-probability model;
- strided allocation is not universally superior to other allocation policies;
- migration maps do not make dense ranks stable across edits;
- rank shrinking is not a universal semantic minimizer;
- scheduler-neutral shards do not prove every external cluster runtime;
- self-reproduction is not independent reproduction.

Those boundaries are part of the evidence, not caveats to be hidden from it.
